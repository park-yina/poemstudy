# Luda Log 프리뷰

## 프로젝트 개요


Luda Log는 단순히 프로젝트 결과물을 나열하는 포트폴리오 사이트가 아닙니다.

기존에는 노션 및 깃허브 블로그를 활용하여 프로젝트를 정리하고 있었습니다.

노션은 각각의 프로젝트를 설명하고 기록하는 데에는 큰 장점이 있었고,
깃허브 블로그나 레포지토리 내부의 docs 문서와 함께 사용할 때에도 좋은 시너지가 있었습니다.

특히 프로젝트를 상태별로 분리하고,
운영 기록과 구조를 함께 관리할 수 있다는 점은 매우 매력적이었습니다.

하지만 실제로 사용하면서 몇 가지 한계를 느끼게 되었습니다.

노션은 계층형 문서를 지원하지만,
동시에 완전한 구조형 문서 시스템이라고 보기도 어려운 독특한 탐색 방식을 가지고 있습니다.

그 결과:

- 프로젝트 규모가 커질수록 탐색 흐름이 복잡해지고
- 문서 간 관계를 직관적으로 파악하기 어려워졌으며
- 단순히 읽는 것 자체에도 러닝 커브가 생기기 시작했습니다.

사람인이나 잡코리아의 이력서는 지나치게 성과 중심이며,
깃허브나 기술 블로그는 문제 해결과 구현 과정 중심의 기록에 가까웠습니다.

노션은 이 두 성향의 중간 지점에 가까웠지만,
결국 플랫폼 자체의 구조 안에서 문서를 구성해야 한다는 한계가 존재했습니다.

실제로 최근 면접을 다녀온 한 회사의 대표님께서는,
이력서를 읽으며 인간 박이나에 대한 호기심은 생기지만
그 사람 자체를 충분히 설명해주지는 못하는 것 같다는 말씀을 해주셨습니다.

특히 저는 단순 결과물이 아니라:

- 왜 이런 구조를 선택했는가
- 어떤 운영 경험이 있었는가
- 어떤 고민 끝에 구현 방향이 결정되었는가

를 함께 기록하고 싶었습니다.

그래서 단순 블로그 대신,
제 색깔과 구조를 직접 담아낼 수 있는 웹사이트를 만들기로 결정했습니다.

기존 깃허브 블로그가
트러블슈팅과 기술적인 문제 해결 중심의 기록이라면,

Luda Log는 보다 상호작용적인 형태의 archive를 목표로 하고 있습니다.

서울예술대학교 재학 시절 접했던 p5.js와 인터랙티브 작업 경험들을 바탕으로,
단순히 읽는 문서가 아니라
사용자가 직접 탐색하고 반응하는 형태의 개발 아카이브를 만들고 싶었습니다.

## 핵심 방향성

Luda Log는 다음과 같은 방향의 고민을 해결하고자 만들어졌습니다.

### 기록 중심 구조

Luda Log는 버전 관리와 계층형 문서 구조를 기반으로,
기록 자체를 중심으로 탐색할 수 있도록 설계하였습니다.

기존 깃허브 블로그(minimal mistakes)의 경우,
카테고리와 하위 카테고리를 비교적 자유롭게 구성할 수 있다는 장점이 있었습니다.

하지만 프로젝트 규모가 커질수록:

- 시리즈 형태의 문서를 하나의 흐름으로 관리하기 어려워졌고
- 문서 간 관계를 구조적으로 연결하는 데에 한계가 있었으며
- 썸네일이나 카테고리 표현을 위해 문서 외적인 관리 비용이 점점 증가하기 시작했습니다.

특히 단순 게시글 구조에서는,
운영 기록이나 구조 설계처럼 서로 강하게 연결된 문서들을
하나의 archive 흐름으로 보여주는 데에 어려움이 존재했습니다.

그래서 Luda Log에서는
문서를 단순 게시글이 아니라,
하나의 기록 시스템처럼 탐색할 수 있는 구조를 목표로 하였습니다.
---

### LudaRota

프로젝트를 정리하면서 느낀 점 중 하나는,
면접관들은 단순 결과물보다
해당 프로젝트에서 어떤 문제를 경험했고,
그 문제를 어떻게 해결했는가를 더 궁금해한다는 점이었습니다.

특히:

- 이슈 탭에서 어떤 고민이 오갔는가
- Actions의 빌드 실패를 어떻게 해결했는가
- 운영 중 어떤 구조적 문제가 발생했는가

와 같은 과정은 실제로 많은 관심이 집중되는 영역이었습니다.

LudaRota는 이러한 문제 해결 과정과 구조적 고민들을
하나의 archive 형태로 모아 보여주기 위해 기획되었습니다.

또한 예술대학교 재학 시절 경험했던
스토리텔링과 인터랙티브 작업 경험을 함께 녹여내고자 했습니다.

단순 프로젝트 목록 대신,
사용자가 직접 탐색하고 해석하는 형태의 구조를 만들고 싶었고,
그 과정에서 타로카드라는 인터랙션 중심의 장르를 선택하게 되었습니다.

이를 통해:

- 개발자로서 어떤 문제를 고민했는가
- 어떤 방식으로 구조를 설계했는가
- 실제 이슈에 어떻게 대응했는가

를 보다 직관적이고 인상적으로 전달하고자 했습니다.

### Runtime 기반 UI

Luda Log의 Workspace는
단순히 파일을 탐색하는 구조가 아니라,
선택한 파일의 종류에 따라 서로 다른 runtime이 실행되는 형태를 목표로 설계하였습니다.

특히:

- 확장자에 따른 프리뷰 구조 변경
- Code Workspace와 Docs Workspace의 분리
- Runtime 기반 Preview UI
- 문서 유형에 따른 Viewer 전환

등의 구조를 통해,
일반적인 markdown viewer보다
실제 시스템 내부를 탐색하는 듯한 경험을 만들고자 하였습니다.

예를 들어:

- 코드 파일은 IDE 형태의 workspace로
- 문서 기록은 manuscript viewer 형태로
- PROJECT LOG는 terminal runtime 형태로

각각 다른 방식으로 동작하도록 구성하였습니다.

이를 통해 단순히 문서를 읽는 데에 그치지 않고,
하나의 fake operating system 내부를 탐험하는 듯한 archive experience를 목표로 하였습니다.

특히 최소화 시 taskbar에 아이콘이 등록되는 구조와 같이,
작은 UI 디테일까지 실제 운영체제의 흐름을 참고하여 설계하고자 하였습니다.

## 기술 스택 선정 이유

### Docusaurus

Luda Log는 Docusaurus 기반으로 구축되었습니다.

선정 이유는 다음과 같습니다.

- markdown 기반 문서 관리
- versioning 지원
- category 기반 archive 구조
- 계층형 문서 탐색 구성
- 검색 시스템 확장 용이성
- generated-index 기반 문서 아카이브 구성
- React 기반 커스텀 UI 확장 가능

특히 Docusaurus의 category와 generated-index 구조는,
문서를 단순 게시글이 아니라
하나의 archive처럼 탐색할 수 있도록 구성하는 데에 큰 도움이 되었습니다.

또한 검색 시스템과 계층형 카테고리 구조를 비교적 자유롭게 구성할 수 있었기 때문에,
프로젝트 규모가 커지더라도 문서 흐름을 유지하기 용이했습니다.

특히 versioning 기능은
단순 문서 버전 관리가 아니라,
운영 기록의 스냅샷을 보존하는 방향으로 활용하고 있습니다.

---

### React 기반 구조

Docusaurus는 React 기반으로 동작하기 때문에:

- runtime UI
- workspace interaction
- animated overlay
- custom archive component

등의 구조를 자유롭게 확장할 수 있었습니다.

이를 통해 단순 문서 시스템이 아니라,
컨셉에 따른 archive room과 interactive runtime experience를 구현할 수 있었습니다.

Luda Log는 기본적인 문서 관리 기능 위에,
사용자가 직접 탐색하고 반응하는 형태의 archive 구조를 구축하는 방향으로 설계되었습니다.

---

### P5.js의 활용

p5.js는 사용자와의 인터랙션과 분위기 연출을 위하여 활용되었습니다.

Luda Log에서는 단순 애니메이션 효과보다는,
archive room 특유의 고요하고 정적인 분위기를 표현하는 데에 집중하였습니다.

특히:

- 먼지 파티클 효과
- 공간감 표현
- 촛불 및 ambient animation
- 사용자 움직임에 따른 인터랙션

등의 요소를 통해,
아카이빙 룸이 하나의 정적인 문서 페이지가 아니라
실제로 존재하는 공간처럼 느껴지도록 구성하였습니다.

또한 서울예술대학교 재학 시절 경험했던
인터랙티브 작업과 디지털아트 감각을 함께 녹여내고자 하였습니다.
---

## 주요 구성 요소

### DevWIKI

프로젝트를 나무위키에서 영감을 받아 구성한 기록형 개발 문서 시스템입니다.

특히:

- 왜 이런 구조를 채택했는가
- 당시 어떤 기술적 판단이 필요했는가
- 어떤 병목이 발생했는가
- 그것을 어떤 방식으로 추적하고 분석했는가

를 중심으로 기록하는 데에 초점을 두었습니다.

일반적인 포트폴리오는 보통:

- 누가 무엇을 만들었는가
- 어떤 기술을 사용했는가
- 어떤 기능을 구현했는가

를 가장 우선적으로 설명합니다.

하지만 실제 운영 환경에서는:

- 구조 선택의 이유
- 실패한 설계
- 운영 중 발생한 문제
- 성능 및 비용 문제
- 예상하지 못했던 예외 상황

같은 요소들이 훨씬 중요하다고 생각했습니다.

DevWIKI는 이러한 과정들을 단순 결과물이 아닌  
“운영 기록”의 형태로 남기기 위해 만들어졌습니다.

특히 저는:

> 위기에 봉착한 개발자가 어떤 선택을 했는가

를 기록하는 것이,  
단순 기능 소개보다 더 중요한 개발 경험이라고 생각했습니다.

따라서 문서에는:

- 실제 구조 변경 과정
- 폐기된 아이디어
- 병목 추적 과정
- 운영 중 발생한 트레이드오프

까지 함께 포함됩니다.

---

### 워크스페이스

IDE 환경과 DOS Runtime,
그리고 삼성의 ONE UI에서 영감을 받아 설계한 아카이브형 작업 공간입니다.

단순 문서 리스트가 아닌:

- 실제 파일 탐색기처럼 탐색할 수 있는 구조
- 작업 중인 기록을 열람하는 흐름
- 런타임 기반의 작업 환경 경험

을 만드는 데에 초점을 두었습니다.

특히:

- 코드와 문서 뷰어의 분리
- 확장자별 Preview 시스템
- Runtime 기반 Overlay UI
- Workspace 형태의 탐색 구조

를 중심으로 설계되었습니다.

예를 들어:

- markdown 문서는 워드와 같은 문서 전용 프리뷰 형태로,
- code 파일은 IDE 스타일 preview 형태로,
- PDF 및 HTML 문서는 별도의 viewer 형태로

동작하도록 구성되어 있습니다.

또한 단순히 파일을 보여주는 것이 아니라,
“기록을 탐색한다”는 감각을 유지하기 위해
탭 구조와 preview 흐름, runtime overlay 등을 함께 구성하였습니다.

차후 모바일 환경 지원 시에는,
삼성 ONE UI의 어플리케이션 전환 경험에서 영감을 받아:

- 앱 전환형 workspace
- 모바일 전용 preview 흐름
- touch 기반 archive navigation

등을 추가적으로 지원할 예정입니다.

현재 Workspace Runtime은
데스크탑 환경에 최적화되어 있으며,
모바일 환경은 아직 지원하지 않습니다.

---
### Manuscript Viewer

문서를 dashboard나 admin panel처럼 보여주지 않고,
실제 manuscript 혹은 기록 문서처럼 읽히도록 구성하였다.

typography와 whitespace를 중요하게 다루고 있다.

---

### Runtime Log System

PROJECT LOG와 DEV LOG는
실행중인 terminal process처럼 보이도록 구성하였다.

단순 code block이 아니라:

- boot sequence
- runtime session
- operational log

등의 분위기를 표현하는 방향으로 설계하였다.

## 지향하는 포트폴리오 방향

Luda Log는 결과만을 보여주는 사이트보다,
운영과 구조를 함께 기록하는 archive를 목표로 한다.

특히:

- 운영 중 발생한 문제
- 구조적인 의사결정
- runtime 설계
- UX 방향성
- 실제 사용 환경에서의 고민

등을 지속적으로 기록하고 정리하는 방향을 지향한다.

이 archive는 단순 포트폴리오를 넘어,
개발 과정 자체를 남기는 기록 시스템을 목표로 한다.
