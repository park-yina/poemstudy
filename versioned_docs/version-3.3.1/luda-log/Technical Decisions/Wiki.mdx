<summary id="wiki-structure-background">

  <span className="wiki-fold-title">
    Wiki 구조 설계 배경
  </span>

</summary>

<div markdown="1">

초기에는 프로젝트 진행 과정에서 발생한 문제들과 트러블 슈팅 내용을  
기술 블로그 및 각 프로젝트 레포지토리 내부의 Docs 폴더에 분산하여 기록하고 있었다.

하지만 프로젝트 수가 증가하기 시작하면서:

- 특정 프로젝트의 기록 흐름을 따라가기 어려워졌고
- 기술 블로그 구조상 운영 과정과 의사결정 기록이 단절되기 쉬웠으며
- 단순 게시글 형태로는 실제 개발 맥락을 유지하기 어려웠다.
- 또한 Docs 폴더 기반 관리는 정보가 산발적으로 분리되기 쉬웠고,
  이를 극복하더라도 결국 "파일 단위 탐색"이라는 한계를 벗어나기 어려웠다.

<DocsRef>

기술 블로그는 minimalMistakes 테마 기반으로 직접 커스텀하여 사용하고 있었기 때문에,
문서 하나를 작성하는 과정에서도 레이아웃과 포맷 관리에 많은 부수 작업이 필요했다.

초기에는 Notion을 활용한 트러블 슈팅 정리도 진행하였으나,
노션 역시 하위 카테고리를 반복적으로 따라 들어가는 계층형 탐색 구조였기 때문에
읽는 사람 입장에서도 탐색 피로도와 러닝 커브가 존재하였다.

</DocsRef>

따라서 해당 문제들을 해결하기 위해:

- markdown 파일 단위 관리
- versioning 시스템
- category 기반 분류 구조
- theme 기반 archive 분리
- footnote 기반 보조 설명
- 검색 시스템

등을 지원할 수 있는 Wiki 구조를 설계하게 되었다.

이는 단순 게시글 아카이빙이 아니라:

> 운영 과정 자체를 하나의 흐름으로 읽히게 만드는 구조

를 구축하기 위한 선택이었다.

</div>

<summary id="wiki-separation">

  <span className="wiki-fold-title">
    Archive Wiki와 Dev Wiki를 분리하지 않은 이유
  </span>

</summary>

<div markdown="1">

해당 기술 의사 결정 문서에서는  
Archive Wiki와 Dev Wiki를 별도의 시스템으로 구분하여 설명하지 않는다.

이는 두 시스템 모두:

- "기록 기반 탐색"
- 백과사전 형태의 구조
- category 기반 문서 탐색
- manuscript 스타일 문서 구성

이라는 공통된 설계 철학을 공유하고 있기 때문이다.

<DocsRef>

메인 기술 스택 역시 모두 Docusaurus 기반으로 동일하며,
실제 차이는 "어떤 기록을 얼마나 드러낼 것인가"에 가까웠다.

즉 구조 자체의 차이보다는:

- 연출 방식
- 분위기(theme)
- 공개 범위
의 차이에 가까웠기 때문에,
별개의 엔진처럼 분리하여 설명하지 않았다.

</DocsRef>
</div>

</details>

<div markdown="1">

LudaLog의 위키를 제작당시 가장 많이 참고한 플랫폼은 나무위키이다.
따라서 theme색상을 통한 미세한 변화를 주는 것 역시 해당 플랫폼에서 차용한 시스템이다.
<DocsRef>
theme색상 도입 이후 가장 눈에 띄는 변화는 프로젝트 별, 혹은 더 작은 단위의 분류 별로
성격을 정해줄 수 있다는 것이다.
대표적인 예시로 LudaLog라는 하나의 시스템을 서술하는 데에
WIKI,Archive,Workspace,LudaRota등의 테마가 사용되었다.
</DocsRef>

<div markdown="1">

manuscript 형태의 가장 큰 장점은 원고 형태로, 각주와 본문의 분리가 가능하다.
따라서 독자가 원하는 방식의 리딩이 가능하기 때문에 해당 형태를 착안하게 되었다.
<DocsRef>
제작자인 루다의 의도는 아니나, 그녀의 전공이 문예창작이라는 것을 고려한다면
간접적으로 자신의 성질에 대한 어필이기도 하다.
</DocsRef>

<div markdown="1">
해당 위키의 MVP모델이 나온 직후부터 검색시스템을 우선 설계하였다.
초반 검색 모델의 경우, 검색어 일치시에만 검색이 가능하였으나 현재에는
연관검색어 대소문자 변환 공백 변환 등이 자동으로 제공되고 있다.
<DocsRef>
차후에는 점핑배틀 랭킹 시스템과 유사하게 유사 검색어에 대한 결과 역시 제공할 예정이다.
문자열 유사도나 거리 알고리즘의 병행 사용으로,
예를 들어 LudaRota의 오타로 Ludarot를 검색 할 경우 유사 검색어 결과를 띄울 계획에 있다.
</DocsRef>
